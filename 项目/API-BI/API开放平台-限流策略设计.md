# API开放平台-限流策略设计

## 1. 写在前面：为什么需要限流

虽然API开放平台是一个学习项目，但是核心的限流策略还是要有的。

没有限流，假如访问量过于大，就可能导致API服务罢工，两边都不讨好。

我们常一说到限流，就开始想到各种各样的组件：redisson-RateLimiter、sentinel组件...

但是我认为组件选型是其次，我们应该如何设计限流策略，才是重点。

## 2. 限流，限哪里的流？

我们来看一下请求流图吧：

![image-20241107142308020](https://web-tilas-zhaozhong.oss-cn-shenzhen.aliyuncs.com/zhaozhong-typora-resources/202411071423170.png)

可以看到，我们其实是有两个地方做限流的：网关，以及API。

那么我们应该怎么设计这个限流策略呢，网关全盘代理，还是各个API有各个API的策略。

需要考虑的是，不同的API接受能力也不同，也就是说如果通过网关一刀切，那可想而知一定会出事。

但是，全部交给API来做，每个API都要去做限流，这样也不是个办法。

基于这种情况，不知道聪明的你有思路了吗？

我的思路就是：直接通过表来规定各个API的限流参数，并提供一套默认的限流策略。API在接入时直接填入限流参数，不就能灵活接入限流了吗？

思路清晰后，我们就开始着手限流策略选型和编码吧。

## 限流，怎么限流？

比较热门的限流组件有基于redis的redisson，或者流量管控方案组件Sentinel，甚至SpringCloudGateway都有能够提供限流器的filter。

眼花缭乱，我们该怎么选择？

我认为技术选型的一个重要策略是：选最适合本项目的技术，而不是最好的技术。

我们来对比一下以上提到的技术方案吧：

### redisson实现的RateLimiter：

redisson实现的RateLimiter主打一个简单高效。我们需要做的事情就是写好配置，创建客户端，定义好限流的Key策略，就完成了。

优点就是十分的简单，而且redisson通过异步进行限流，因此无需担心Redis挂掉的问题。

缺点的话，就是动态更新比较薄弱，一旦定制好限流器，想要动态更新，就必须得删除Redis中的限流器，重新生成。当然这个也是可以通过编码实现，但是就会变的复杂。

### Sentinel：

Sentinel作为一个微服务的流量管控组件，它的定位更多的是在微服务上。我认为API平台并不是很契合这个组件，其一是因为Sentinel太大了，我仅需一个限流器即可。其二是系统架构就决定Sentinel的方案不对。假如系统有很多API，就要对每个API添加进Sentinel，这对于耦合性也是比较差的。

### SpringCloudGateway的限流器：

SpringCloudGateway尽管有限流器，但是这个限流器是全局的，想要定制限流器，就需要重写AbstractRateLimiter。十分麻烦，因此不建议使用。

所以这边我们就直接采用Redisson的RateLimiter实现限流策略。
